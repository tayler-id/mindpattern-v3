01The opening answer

They will open with some version of "so what is it?" You have about ninety seconds before they decide how technical to go. Lead with the shape of the thing, not the stack.

Say something like this

It's a research pipeline that runs itself every morning. At five o'clock a job wakes my Mac, pulls from eight sources, then launches thirteen separate Claude processes that each go and research one beat. Their findings get deduped against about twenty-one thousand things the system already knows, and two more Claude calls turn what survives into a ten-thousand-word newsletter that lands in my inbox thirty minutes after it starts. Then it publishes a public site, scores its own output, and edits its own notes about how it's doing. It's been doing that for 179 days.

That answer works because it is concrete, it has a number in almost every clause, and it ends on a fact that is hard to argue with. It also sets up the two questions you actually want them to ask, which are how the thirteen agents work and how much of it the model is really deciding.

Then the framing that carries the whole rest of the conversation:

The line to plant early

Python owns control flow. Claude owns judgment and prose. The model never decides what happens next, and there is no line of code anywhere in the project where a model's output picks the next step.

Plant that early and everything afterwards has somewhere to attach. Every design decision in the system is downstream of it, including the ones that turned out to be wrong.

02Words you'll have to define

These are all invented, and none of them mean anything outside this repo. In an interview you will reach for them without noticing. Here is the one-sentence version of each, so you can define it in stride instead of stalling.

preflight
The deterministic gathering pass that runs before any model does. Plain Python pulls from eight sources in parallel, tags each item as new or already-covered, and routes it to whichever agent owns that beat. The agents never start from a blank page.
a finding
One atomic research result: a title, a two or three sentence summary, an importance rating, and a source URL. Findings are the currency of the whole system. Everything downstream operates on them, and there are 21,307 in the database.
a phase
One of twelve fixed steps the pipeline moves through in a strict order. Two of them are critical, meaning the run dies if they fail. The other ten degrade and the run keeps going.
an agent (here)
Not a subagent inside a session. A separate operating-system process running the Claude CLI, with its own context window, its own tool budget, and its own timeout. Worth stating explicitly, because most people will assume you mean the other thing.
a skill file
A markdown file that defines one agent. The file is the agent. There is no per-agent Python. Editing the markdown changes behavior the next morning, and the system notices the file changed and watches whether quality moved.
the vault
An Obsidian folder of markdown the system writes about itself: its identity files, daily notes, one page per source. SQLite is the source of truth and the vault is a readable copy.
soul.md, voice.md, user.md
Four identity files that get loaded into every agent prompt and both writing passes. soul.md is the system's sense of its own purpose, voice.md is the writing guide, user.md is who it's writing for, decisions.md is its running journal.
a gate
A point where the pipeline stops and waits for you in Slack. Gate 1 approves the social topic before anything is written. Gate 2 approves the finished drafts before anything is posted.
the EIC
Editor-in-Chief. The agent that reads the day's findings and either picks the one thing worth posting about or declares a kill day.
a kill day
The EIC deciding nothing today clears the bar, so nothing gets posted. Worth mentioning unprompted, because a system with permission to publish nothing is more interesting than one that posts daily no matter what.
the expeditor
The last automated quality check before a human sees a draft. It reads the complete package and returns pass or fail.
a receipt
A row claimed in the database before any irreversible external action, keyed like newsletter:2026-08-20. Claiming it twice fails, so a crash-and-resume physically cannot send the same email twice.
the harness
A second, separate loop where agents find issues in the codebase, plan fixes, write tests first, and open pull requests. Not part of the daily run. Explained honestly in the audit section, because it is currently dormant.

03The design bet

If the book has a thesis-shaped hole in its agentic-systems chapter, this is what goes in it. Take your time on this one.

The bet is that you get a reliable system by making the boundary between deterministic code and model judgment explicit, and then defending it. Not by making the model smarter, and not by adding more agents. By being strict about which decisions a model is allowed to make at all.

In practice that means orchestrator/pipeline.py is a 158-line state machine with a frozen phase order and a transition table. A phase can move to the next phase in the sequence, to failed, or to completed. Anything else raises an exception. The model has no input into that, ever. What the model does get is bounded and specific: read this evidence and form a judgment, or take this material and write it well.

The reason this matters is not philosophical, it is operational. Prompting is stochastic and a pipeline that ships to subscribers every morning cannot be. Here is the story that proves it, and it is a good one to tell because it is small and completely unambiguous.

The em-dash experiment nobody meant to run

The house style bans em dashes. The rule was in the voice guide, which is loaded into the newsletter writer's prompt on every single run. On 25, 26 and 27 July 2026 the same model, the same prompt and the same voice guide produced 42 em dashes, then 2, then 52. Nothing changed between those runs except the sampling.

The lesson is not that the model is unreliable. It is that asking harder was never going to close that gap, because the gap is variance and instructions do not remove variance. So the rule moved out of the prompt and into orchestrator/prose_gate.py, a deterministic pass over the finished text with a budget of six per issue, protected spans so an em dash inside a code block or a URL is left alone, and a repair step. The count has been in range every run since.

The generalization is the quotable part, and it is worth having ready in one sentence.

Say something like this

Anything a regular expression can check, code checks, and I stopped asking the model for it. Anything that needs taste stays in the prompt, because code can't do taste. The mistake I kept making early on was putting mechanical rules in the prompt and then being surprised when they held four days out of five.

There is a second-order version of this that is more interesting and slightly less flattering, so save it for when they push. The boundary is not free. Every time you move a rule from the prompt into code you add a piece of machinery that can itself rot, and about half the things I found when I audited this system properly were pieces of that machinery quietly doing nothing. The audit section has the details.

04How Claude actually gets called

This surprises people, so it is worth landing clearly. There is no API integration. Every model call in this system shells out to the Claude Code command-line tool as a subprocess.

No anthropic package in the requirements file. No API key anywhere in the project. It runs on a personal Claude subscription through the CLI in print mode, which means non-interactive, one prompt in, text out, no session. A single 78-line module, core/claude_cli.py, is the only place the system touches a model.

claude -p "<the whole prompt>" \
  --model opus \
  --max-turns 35 \
  --output-format text \
  --append-system-prompt-file prompts/research-agent-system.md \
  --allowedTools WebSearch \
  --allowedTools WebFetch \
  --allowedTools "Bash(mcporter call *)" \
  --allowedTools "Bash(twitter *)" \
  --allowedTools "Bash(yt-dlp *)"

Three implementation details in that wrapper are worth knowing, because each one exists because something broke.

The subprocess gets its own process group. start_new_session=True, so when a thirty-minute timeout fires it kills the CLI and every tool process the CLI spawned. Without that you leave orphaned yt-dlp children running after the agent is gone.

The environment carries the agent's identity. Three variables go into the child process so a session-end hook can file that agent's transcript in the right folder for later analysis. It is how you get per-agent forensics out of a system that is just spawning processes.

Prompts over 100,000 characters go through stdin instead of an argument. Past that the operating system's argument limit truncates silently. The synthesis prompt crosses that line most days, because it carries the entire day's findings.

Three shapes of call, and why there are three

Every model call in the system is one of three patterns, distinguished by where the output lands. That distinction turns out to matter more than it sounds.

PatternWhere output goesWho uses it
run_single_agent()JSON on stdout, parsed by a balanced-brace scannerThe 13 research agents
run_claude_prompt()stdout is the deliverable, published as-isThe newsletter writer, story selection, social drafts
run_agent_with_files()The agent writes a file, Python reads it backEIC, art director, critics, expeditor

The middle one is the dangerous pattern and it is worth saying why. When stdout is the newsletter, anything the model prints becomes the product. There is a check called _is_bare_api_error() whose entire job is to notice that the CLI printed "API Error: connection closed mid-response" to stdout with a zero exit code, because without it that string becomes the newsletter. It is anchored to the start of the text so a story that is genuinely about API errors still publishes fine.

Tool grants are pre-approvals, not a sandbox

People assume --allowedTools is a fence. It is not. It grants the listed rules without a permission prompt; read-only tools work regardless. Two rules govern what goes on that list.

Raw curl is deliberately never granted, because scraped web content must not reach a shell that can make outbound POST requests. Deep page reads go through WebFetch instead. And every shell grant must name a binary that is actually installed, which is checked at dispatch time by a function called missing_granted_binaries(). That check exists because of one of the better failure stories in the whole project.

The grant that agreed with the prompt and was still wrong

On 24 July 2026 the grant list allowed a tool called xreach and the research prompt told all thirteen agents to run xreach search. Grant and prompt matched perfectly. The tool had been replaced a month earlier and was not installed. Agents hit a missing binary and, rather than make something up, several of them refused in prose and the day's research degraded.

The point worth making in a book is that internal consistency between your prompt and your config proves nothing. Both can be consistently wrong. The only check that would have caught it was one against reality, so now the dispatcher looks up every granted binary on the PATH before it starts and warns.

The system prompt does exactly one job

Execution context lives in a separate file appended as a system prompt, never in the task text. That sounds like a stylistic choice and it is not.

On the same bad day in July, seven of thirteen agents declined their task. Their reasoning, in their own words, was that the prompt looked like a transcript someone had pasted into an interactive Claude Code session, and that complying would mean fabricating a payload of twenty findings. Both readings were wrong, but they were reasonable readings of what the agent could see.

The fix is small and generalizes well. User input cannot credibly assert that no human is present, because user input is exactly what a human would type. Put that claim in the system prompt, where it is a property of the harness rather than a claim inside the message. The same file also states plainly that the finding count describes a normal day rather than a quota, and that returning fewer real findings is always the correct behavior. Refusal rates went to roughly zero.

If they ask what the hardest scheduling problem was

Getting a laptop to be a reliable server. The scheduler fires every fifteen minutes across a five-hour window, so nineteen of the twenty triggers do nothing. That sounds wasteful until you learn that macOS skips its scheduled wake when the machine is on battery, and both the power daemon and the calendar scheduler had silently drifted onto the wrong timezone after I moved. Dense triggers mean the run starts within fifteen minutes of the first time the lid opens, instead of waiting for the next hour.

06The thirteen agents, in depth

This is the part they will want to slow down on, so it is worth being able to explain it three levels deep. Start with what they are, then how they are dispatched, then what happens to what they bring back.

What an agent actually is

Thirteen markdown files in one directory. That is the whole roster. Each file is between 65 and 162 lines and names the specific sources, people, subreddits and quality bar for one beat. There is no Python behind any individual agent. When the pipeline dispatches, it reads the markdown, wraps it in a standard scaffold, and hands the result to a fresh Claude process.

Correct people early if they picture subagents inside a session, because it changes what the design is doing. Each agent here is a separate operating-system process with its own context window, its own tool budget and its own thirty-minute timeout. Python owns the fan-out with a thread pool that runs six at a time, so seven of the thirteen are queued at any moment.

Six rather than thirteen is a throttle, and the reasoning is worth having ready because it is a nice systems answer. When all thirteen hit rate limits at the same moment, their retries become the next overload. So the backoff uses full jitter, a random delay drawn from zero up to the current cap, rather than a fixed wait. Fixed backoff would just reassemble the wave one step later.

Why thirteen rather than one big agent

Three reasons and they compound. Context isolation, so a heavy paper day can't crowd the security beat out of the window. Failure isolation, so one agent timing out costs a thirteenth of the day instead of everything. And prompt specificity, because each file can name real sources and a real quality bar for its beat, and a single prompt covering all thirteen beats cannot be that specific about any of them.

What goes into one agent's prompt

Nine blocks in a fixed order. The output contract appears at both the top and the bottom, because instruction-following degrades in the middle of a long prompt and the contract is the one thing that cannot be missed.

  1. The JSON schema, and the words "output ONLY valid JSON"
  2. The system's identity file, so every agent shares a sense of what the project is for
  3. The file describing who the newsletter is written for
  4. That agent's own skill file, its domain and sources and quality bar
  5. Memory: this agent's findings from the last seven days, its best-performing sources, what the other twelve agents have already found today with semantic overlap flagged, and cross-agent patterns learned over time
  6. Today's detected trends
  7. The pre-fetched items routed to this agent, with anything already covered struck through and dated
  8. Instructions for going past the pre-fetched set using semantic search, page fetching, Twitter and YouTube
  9. A novelty requirement and a mandatory six-point self-critique the agent must run before emitting anything

The self-critique block is the one worth quoting, because it is doing the most work for the least machinery. Before it outputs anything the agent has to drop any finding whose primary source is older than 48 hours, any topic already covered in the last ten days without genuinely new data, and any rewrite that adds nothing to the original. Anything it can only find one source for gets downgraded rather than dropped.

What happens to what comes back

Findings do not go straight into the database. Four gates stand between an agent's output and storage, and they check different things on purpose.

  1. Cross-agent dedup. All findings from all thirteen agents get embedded and compared to each other. Near-duplicates above 0.85 collapse to whichever copy scores better on summary depth, importance and having a source URL.
  2. The policy engine. Required fields, a valid importance value, URL sanity, banned entities, and eight named prompt-injection patterns. This runs before storage, so bad findings never enter memory rather than getting cleaned up later.
  3. The stale-source gate. If a URL's own path encodes a date more than thirty days old, it is recycled content rather than news. No embeddings involved, just string parsing, which means it works even when everything else is having a bad day.
  4. The history gate. Semantic similarity above 0.90 against 180 days of stored findings.

On 20 August, 189 findings survived all four. If zero survive, the phase raises and the whole run fails, on the grounds that a newsletter with no research behind it is worse than no newsletter.

When an agent fails

The CLI writes API errors to standard output, sometimes with a zero exit code, so the classifier reads both streams and sorts every failure into one of five buckets: overloaded, rate limited, server error, parse error, or other. The first three retry with jittered backoff up to three attempts. Parse error gets exactly one corrective retry with explicit headless framing appended, because a clean exit with unparseable output almost always means the model wrote an essay instead of JSON. Above all of that, the phase re-dispatches any agent that finished with an error and nothing to show, once, on the theory that a transient cause has usually passed by the time the first wave finishes.

Why that re-dispatch exists

On 19 August 2026 the Mac was on battery and went to sleep mid-run. Twelve of the thirteen agents died mid-response and a twelve-finding issue went out. Software cannot prevent that sleep. What it can do is warn at the very start of the run while the warning is still useful, and give a dead agent one automatic second pass. Both of those exist now because of that morning.

07All twelve phases

Reference material. You will not walk through all twelve out loud, but you should be able to answer a question about any of them without hedging.

01Init■ mostly Python

Housekeeping with one model call in it. Checks whether the Mac is on battery and sends a Slack warning if so. Pulls in anything posted from your phone. Fetches reply emails, and if any are unprocessed, sends them to a small Claude call that extracts topic preferences and writes them as numeric weights the story selector reads later. Then hashes every prompt file in the project so that if quality moves tomorrow, the system can point at which prompt you edited.

02Trend scan■ no model at all

This used to be a Claude call and now has none, which is a small story worth telling because it runs the design bet in reverse. Eight source modules run concurrently on a thread pool. Everything they return gets embedded locally and compared against ten days of stored findings, with anything above 0.85 similarity tagged as already covered, carrying the date and the agent that first found it. A time-decay curve loosens that threshold for older matches, so a story that has genuinely developed is not censored for resembling its own earlier version.

Trends then come out of clustering those items by similarity and scoring the clusters on engagement and source diversity. No judgment required, so no model required. It also means a resumed run can redo this step for free, which matters when something crashes.

03Research◆ 13 to 26 processes■ critical

Covered in full in the previous section. One of the two phases where failure kills the run.

04Synthesis◆ 2 Opus passes■ critical

Pass one picks the stories. It gets the day's findings after a source-rebalancing step, each one carrying an inline marker if a past issue already cited that URL, plus your preference weights, the trend list, and a formatted block of every story published in the last twenty-one days. It returns exactly five stories with reasons.

Then a deterministic tripwire compares that selection against the published archive by word overlap. If it repeats something, the pipeline forces exactly one re-pick with the offending titles named. If the second attempt still repeats, the issue publishes anyway and you get a Slack alert. Never a silent repeat, and never a blocked newsletter.

Pass two writes the issue. Its prompt opens with an output contract that says, in effect, your standard output is published verbatim to subscribers, so emit only newsletter markdown and never mention tools, sessions, finding counts, dedup, or coverage constraints. That last clause is specific and earned: on 19 August a degraded run opened by telling subscribers that the selection pass had only cleared one story.

Three attempts. If all three fail, Python assembles a plain source-list brief from stored findings and sends an urgent alert rather than shipping nothing. Afterwards, all in code: strip any process narration before the first heading, replace whatever headline the model wrote with a deterministic one, run the prose gate, write the file, run the URL tripwire, score the issue on six dimensions, and assess the quality floor.

The quality floor no longer touches the newsletter

It used to be able to. On 13 July 2026 a thin research day tripped the floor and a finished, perfectly good newsletter was replaced by a bare list of links. That is a worse outcome than publishing something slightly weak. Now the floor only reports. It writes to the trace database and alerts Slack, and the issue the writer produced goes out untouched. The general rule that came out of it is that a quality check should be allowed to tell you something is wrong and not allowed to fix it by making it worse.

05Deliver■ no model

Validates the file, appends a feedback footer, converts markdown to HTML, and posts to the email API with both HTML and plain-text bodies, retrying with backoff. Subscribers get a separate broadcast built from the pre-footer copy.

Two safety mechanisms are worth explaining because they are the kind of thing people underestimate until it bites them. A receipt keyed to the date is claimed before the send, so a crash-and-resume physically cannot send twice. And the marker file that tells the scheduler the day is done is written only when delivery is confirmed.

Why that marker moved

On 13 June 2026 the shell wrapper touched the done-marker before running the pipeline. The pipeline then crashed at startup. The marker said the day was finished, so every retry window that morning skipped, and no newsletter went out at all. A bug that lasted one second became an outage that lasted a day. The marker now belongs to the delivery phase and nothing else can write it.

06Site content■ deterministic core◆ writer and critic

Builds the public website. A deterministic engine reads a public-safe view of the corpus, picks candidate stories, assembles an evidence pack for each, and generates the copy. A live writer agent and a desk-editor critic sit on top, and both are entirely optional. If the model is unavailable, or its draft fails a deterministic copy lint, the deterministic version ships instead. That is a design pattern worth naming out loud, because most people build it the other way around and have no fallback at all.

07Learn■ Python◆ one small call

Scores the run and compares it to the seven-day average, storing a lesson if it dropped. Attributes any quality change to prompt files edited since the last run. Extracts entity relationships from high-importance findings. Then the memory lifecycle: cluster the agents' own observations into shared patterns, promote a pattern once enough different agents have seen it, and archive what has gone stale. Read the audit section before you describe this one confidently, because until yesterday most of it was doing nothing.

08Social◆ ~8 agents in sequence

Off by default on scheduled runs, because it needs you at the approval gates. Eleven steps: post anything deferred from yesterday, check rate limits before spending a single token, let the EIC pick a topic, gate 1 in Slack, creative brief, optional illustration, per-platform writers in parallel, blind critics for up to three rounds, deterministic policy validation, a humanizer pass, the expeditor as a final check, gate 2 in Slack, then posting with random jitter inside a configured window.

The detail people react to is the kill day. If the EIC decides nothing today is worth publishing, nothing gets published, and that outcome is recorded as a negative signal rather than as a failure.

09Engagement◆ finder and writer

Finds conversations worth replying to based on the day's research, drafts substantive replies, routes them through the same Slack approval path, then posts and follows. Every follow is receipt-guarded so a retry cannot double-follow anyone.

10Identity◆ one call

The system edits its own identity files. It assembles a summary of the day and asks for a structured diff, which Python then validates and applies with size limits and content sanitizing. Those files are loaded back into every agent prompt the next morning, which is the mechanism by which the loop is supposed to close. Whether it actually closes is covered in the audit.

11Mirror■ no model

Regenerates the database contents as browsable markdown: daily notes, a page per source, topics, people, past issues. SQLite stays authoritative. The vault exists so a human can wander through what the system knows without writing a query.

12Sync■ no model

Bundles the database and the day's reports into a single archive and uploads it in one connection rather than thirty. Restarts the cloud app so it reopens the replaced database file, waits for its warm-up, then requests the day's new pages one at a time so the CDN has them cached before the first reader arrives.

08What broke, and what it taught

This is your strongest material and you should not hold it back. A book about agentic systems is full of people describing architectures that work. Almost nobody brings receipts for the ways theirs failed, and the failures are where the actual knowledge is.

Each of these is a real incident with a date, and each one left a specific piece of code behind. Told in that order, incident then artifact, they land as engineering rather than as confession.

The one that generalizes best

If you only tell one of these, tell 17 August, because it is the one with a lesson that transfers to any system with layered checks.

There were four dedup layers at the time, and all four were working correctly. The problem was that all four compared findings to other findings. Not one of them ever looked at what past issues had actually published. So a story could be re-reported as news, and every gauge stayed green, because no gauge was pointed at the thing that mattered.

Say something like this

I had four deduplication layers and all four passed while the newsletter re-reported twenty-six stories in twenty issues. They were all measuring the same thing from slightly different angles. The fix wasn't a better threshold, it was a check that read the published issues themselves, in plain string comparison with no embeddings in it, so it keeps working on the days everything else is broken.

That last clause is the part worth emphasizing. The new layer is deliberately the dumbest one in the system, stemmed word overlap and nothing else, precisely so it does not share a failure mode with the four sophisticated layers it backs up.

09The honest audit

Yesterday I went through the databases and the git history instead of reading the code, and found that a meaningful share of the self-improvement machinery was running every day and doing nothing. This is the section to volunteer rather than wait to be asked about, and it is genuinely the most interesting thing you can offer a book.

Three loops were built. One was running.

Working. The quality loop. Every run gets scored on six dimensions, compared against the seven-day average, and a drop writes a lesson. That is a real 175-run time series, and the 19 August collapse from 0.719 to 0.573 showed up in it the same day. This part does what it says.

Half working. Identity. It writes genuine daily analysis into its journal and reads the last seven entries back, so there is a real loop turning. But the voice guide, the file that actually shapes the prose, had not changed a single line since 26 June, and the file describing the reader had not changed since 1 July. The loop was turning without moving anything. Worse, because scheduled runs skip the social phase, four of the eight inputs to that prompt arrive absent every day, and the system had been dutifully recording the same missing-telemetry item as an unresolved action for eight consecutive weeks without anything ever reading it back.

Dormant. Pattern consolidation, and the harness. The consolidation step clusters agent observations into shared rules that get fed back into every agent's prompt. It runs daily. It reads a table that nothing has ever written to, so it clusters an empty set and exits. The 223 patterns in that table were all created between 3 March and 9 April, and all thirteen agents had been reading that frozen April snapshot every morning since, labelled as live cross-agent learnings.

The harness, meanwhile, genuinely worked: sixteen pull requests from harness branches, all sixteen merged, between 1 and 3 April. Then it stopped. Every one of its 34 tickets was created in that same three-day window. Its audit log has one line in it, dated 7 May. Its feedback file, the mechanism by which merge decisions were supposed to teach the scout what gets accepted, is an empty array and always has been. There is no scheduler for it. It is a manual command nobody has run in four months.

Do not say "it improves itself" unqualified

You will be tempted, and someone technical will ask what improved and when. The strong version of this answer is the honest one, and it is better material anyway: three loops built, one running, and here is exactly how I found out which was which.

The two bugs underneath

When I dug in, the consolidation failure turned out to be two separate defects stacked, and both are the kind that only show up in production data.

The first is that nothing wrote the input table. The pattern-learning loop was built to consume agent self-observations, and the agents were never asked to produce any. The output schema had findings and nothing else.

The second is subtler and better as a story. The consolidation step loads existing patterns to check whether a new observation matches one, and it filtered on status equals active. But the promotion step, which runs right after, flips any pattern that has matured to status promoted. So the moment a pattern became established, consolidation could no longer see it, and the next matching observation created a duplicate instead of incrementing the original. The bug specifically hit the patterns that mattered most, and it hid inside a code path that had been dormant so long nobody would have noticed either way.

The line that makes this land

The lesson isn't that I had bugs. It's that a loop with no output nobody checks will run in silence for months and look completely healthy from the outside. The learn phase logged a successful consolidation every single morning. It was consolidating nothing. If I hadn't gone and counted rows in the database, I'd have kept telling people it was self-improving.

What is fixed as of today

This is a good thing to be able to say in present tense, because it turns the audit from a confession into a work log. All of it is committed, on a branch, with tests that were watched failing first.

  • Research agents now emit an optional array of self-observations alongside their findings, capped at six per agent, and the research phase persists them. That is the input the consolidation step was always waiting for.
  • The consolidation query now matches against promoted patterns as well as active ones, so an established pattern absorbs new observations instead of spawning a copy.
  • A third bug surfaced while writing a test for the second: the note-storing function inserted its row before computing the embedding, so an embedding failure left an orphan row that the next successful call committed without one. It embeds first now, which makes the write all-or-nothing.
  • Quality-drop lessons now name a cause. Instead of "Overall score 0.573 vs 7-day avg 0.719" they read "only 1/13 agents contributed; agents that errored: hn-researcher, reddit-researcher; sources degraded: reddit".
  • The voice guide and the reader file are now read-only at runtime, after the flat-tone episode in August, and a diff proposing changes to either is discarded and logged rather than applied.
  • Unresolved journal items are fed forward with a count of how many runs have restated them, with instructions to close, restate with evidence, or drop. Anything restated three times without progress is required to be escalated or dropped rather than copied forward again.

The database, honestly

Sixty-one tables across two SQLite files sounds like more system than it is, so I counted. In the main database, fourteen tables are written every run and another five on events. Eight are frozen at various dates between March and July. Five have never held a single row. There is also a full-text index built over the findings table that was never populated, so a search against it returns nothing, though nothing queries it either, which makes it dead weight rather than a broken feature.

The trace database is worse: nine of its eighteen tables are empty, and three of those nine are superseded duplicates of tables that are live. One module still creates the old names on every open while two other modules write the new ones. Two generations of schema, both shipping, neither aware of the other.

If they ask about the dead tables

Every one of them is a feature I started and a decision I never made explicitly. That's what accumulation looks like in a system that only one person reviews. The tables aren't the problem, the problem is that nothing in my process ever asked "is this still true?" until I sat down and asked it by hand.

10Questions you'll get

These are the ones worth having a real answer to rather than improvising. Each of them has a version that is true and interesting, which is better than one that is just impressive.

Is this agentic, or is it just a workflow with LLM calls in it?

Both, at different levels, and the distinction is the whole design. The outer loop is a hard-coded state machine with no model anywhere in the control path. The inner work is genuinely agentic: each research agent runs up to thirty-five turns, decides which tools to use, follows leads it finds mid-run, and applies its own critique before answering. Agency stops at the phase boundary. I would rather have thirteen agents with real latitude inside a rigid frame than one agent deciding what the pipeline does next.

Which model, and what does it cost you?

The Claude command-line tool in headless mode, running against a personal subscription. Research agents and both writing passes are on Opus, using the million-token context variant where the entire day's findings have to sit in one window. Sonnet handles the bounded writing and review work. There is no API key in the project and nothing calls the paid API, which is unusual enough that it is worth saying plainly.

What stops it hallucinating an entire newsletter?

Four things in sequence, and the first one is a prompt decision rather than code. The system prompt states that the finding count describes a normal day rather than a quota, and that returning fewer real findings is always correct, which removes the pressure that makes fabrication attractive. Then the policy engine rejects any finding without a source URL before it is stored. Then the stale-source and 180-day similarity gates drop recycled material. Then the evaluator scores source density in the published text. If the model would rather refuse than fabricate, that is the designed outcome and the pipeline records it as a degraded run.

What was actually the hardest part?

Everything at the seams, where non-determinism meets code that expects a shape. A model refusing in prose where a parser expected JSON. The same prompt producing forty-two em dashes one day and two the next. A tool grant naming a binary nobody had installed. None of those are model quality problems and none of them are fixable by prompting harder. The pattern in every fix is the same: move the check out of the prompt and into code, at the exact point where the failure would otherwise do damage.

How much do you actually trust it?

Enough to let it publish without reading it first, not enough to let it post to social media without an approval gate. That line is where it is because email to my own list is recoverable and a bad post is not. The interesting part is that the trust is not in the model, it is in the gates around it. I would not trust the same model with no prose gate, no dedup layers, and no receipts.

What would you build differently?

Two things. The site-building phase takes two hours and forty-seven minutes and sits inside the same sequential run as everything else, which is architecturally silly. It should be a separate job triggered after delivery. And the second is the audit finding: I built three self-improvement loops and never instrumented whether any of them were producing output. A loop that runs and does nothing looks exactly like a loop that works, right up until you count rows.

Could someone else run this?

The research roster could move to a completely different domain without touching Python, because every agent is a markdown file and the dispatcher checks a per-user override directory before the defaults. What would not transfer is everything shaped by this machine: a laptop scheduler, a macOS keychain, a personal subscription. It is a single-user system that happens to be built like a multi-user one, and I would be honest about that rather than overclaiming it as a product.

11Traps

Specific things to avoid saying, mostly because they are either wrong or because they invite a follow-up you cannot answer cleanly.

Do not say twelve agents

It is thirteen. Thirteen skill files, thirteen dispatched, and thirteen active on eighteen of the last twenty runs. The number appears in the quality thresholds too, so getting it wrong is checkable.

Do not say the research agents run on Sonnet

The docstring in the code still says "13x Sonnet" and it is stale. The router has said Opus for a while and the router is what executes. If you glance at the code mid-interview you will read the wrong thing.

Do not describe the schedule as hourly from 7 to 11

That is what the project README says and it has been wrong for a while. The real schedule fires every fifteen minutes from 05:00 to 09:45, with the wrapper enforcing a 05:00 to 09:59 window.

Do not call `--allowedTools` a sandbox

It is a pre-approval list, not a fence. Read-only tools work whether or not they are listed. If you describe it as a security boundary, a security-minded reader will correctly push back and you will lose the thread.

Do not quote table counts from the README

It says seventeen-plus and fourteen. The real numbers are 43 and 18, and roughly half of those are dead. Use the audit section's version.

One thing to be ready for

If the interviewer is sharp, at some point they will ask whether all this machinery actually produces a better newsletter than a single well-prompted model call would. That is the right question and it deserves a real answer rather than a defensive one.

The honest version: for any one issue, probably not by much. What the machinery buys is that the 179th issue is as good as the 5th, that it does not repeat itself across months, that a bad source day degrades instead of producing confident nonsense, and that when something does break there is a trace explaining which of twelve phases failed and why. That is a reliability argument, not a quality argument, and it is stronger for being framed that way.
