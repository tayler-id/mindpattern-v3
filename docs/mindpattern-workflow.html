A newsletter that writes itself before you wake up

Every morning at 5 AM a launchd job wakes a Mac, pulls from eight data sources, fans out thirteen headless Claude processes, dedupes what they bring back against 21,000 stored findings, writes a 10,000-word issue, emails it, publishes a public site, and then goes and edits its own prompts. This is how each of those pieces actually works.

01The one idea

Python owns control flow. Claude owns judgment and prose. The model never decides what happens next.

That line is not a slogan, it is enforced in code. orchestrator/pipeline.py is a 158-line state machine with a frozen phase order and a transition table. A phase can only move to the next phase in PHASE_ORDER, to FAILED, or to COMPLETED. Any other transition raises ValueError. There is no place in the codebase where an LLM's output selects the next step.

What the LLM does get is bounded and specific: read this evidence, form a judgment, produce text. Story selection, newsletter prose, social drafts, topic scoring, identity edits. Everything around those calls, the scheduling, retries, dedup, validation, storage, delivery, and quality scoring, is plain Python that behaves identically every run.

The split matters because prompting is stochastic and the pipeline is not allowed to be. On 25, 26 and 27 July 2026 the same model, the same synthesis prompt and the same voice guide produced 42, 2 and 52 em-dashes. Asking harder does not close that gap. So the em-dash rule moved out of the prompt and into orchestrator/prose_gate.py, a regex pass over the finished text with a budget of 6 per issue, protected spans for code and URLs, and a repair step. Style you can detect, code enforces. Style that needs taste stays in the prompt.

The rule, stated plainly

If Python can do it reliably, Python does it. The model is called only where judgment is genuinely required, and its output is always parsed, validated, or scored by Python before anything downstream trusts it.

02How Claude is actually called

Not the API. The claude CLI, in headless mode, as a subprocess, on a personal Anthropic subscription.

There is no anthropic package in requirements.txt and no API key anywhere in the pipeline. Every model call shells out to the Claude Code CLI with -p (print mode, no interactive session). One process boundary handles all of them: core/claude_cli.py, 78 lines, wrapping subprocess.Popen.

claude -p "<the whole prompt>" \
  --model opus \
  --max-turns 35 \
  --output-format text \
  --append-system-prompt-file prompts/research-agent-system.md \
  --allowedTools WebSearch \
  --allowedTools WebFetch \
  --allowedTools "Bash(mcporter call *)" \
  --allowedTools "Bash(twitter *)" \
  --allowedTools "Bash(yt-dlp *)"

Three details in that wrapper earn their place:

  • Own process group. start_new_session=True, so a timeout kills the CLI and every tool subprocess it spawned. Without it a 30-minute agent timeout leaves orphaned yt-dlp children behind.
  • Environment carries identity. MINDPATTERN_AGENT, MINDPATTERN_DATE and MINDPATTERN_VAULT go into the child env so a SessionEnd hook can file that agent's transcript in the right folder for later analysis.
  • Big prompts go through stdin. Above 100,000 characters the prompt argument becomes - and the text is piped in, because ARG_MAX would otherwise truncate it. Synthesis prompts routinely cross that line.

Tool grants are pre-approvals, not a fence

--allowedTools grants the listed rules without a permission prompt. Read-only tools work regardless. Two rules govern what goes in the list. First, raw curl is deliberately never granted, because scraped content must not reach a shell that can POST; deep reads go through WebFetch and Jina instead. Second, every Bash(...) grant must name a binary that is actually installed, and missing_granted_binaries() checks PATH at dispatch time and warns.

Why that PATH check exists

On 24 July 2026 the grant list allowed Bash(xreach *) and the research prompt told all 13 agents to run xreach search. The tool had been replaced a month earlier and was not on PATH. Grant and prompt agreed with each other and were both wrong, so internal consistency caught nothing. Agents hit a missing binary and, rather than fabricate, several refused in prose. The whole day degraded.

The system prompt does one specific job

Execution context lives in prompts/research-agent-system.md, appended with --append-system-prompt-file, and never in the task text. User input cannot credibly assert "no human is present", and that is the whole reason. On 24 July, 7 of 13 agents read their task as a transcript someone had pasted into an interactive session and declined it. Moving that framing into the system prompt fixed it. The same file also spells out that the findings count is a description of a normal day, not a quota, and that returning fewer real findings is always correct.

04The twelve phases

Defined in orchestrator/pipeline.py, executed by orchestrator/runner.py (2,761 lines). Two are critical. A failure in either one ends the run. The other ten are skippable and log a warning instead.

01InitPhase.INIT■ Python◆ 1 optional call

skippable · ~14s · writes: traces.db rows, prompt version hashes

Checks whether the Mac is on battery and Slacks a warning if so. Ingests phone-posted journal entries from Fly. Fetches reply emails through Resend and, if any are unprocessed, sends them to Claude with agents/feedback-processor.md to extract topic preference weights, clamped to plus or minus 3 and written to user_preferences. Then orchestrator/prompt_tracker.py hashes every prompt file so the learn phase can attribute a quality drop to a prompt edit.

02Trend scanPhase.TREND_SCAN■ Python only

skippable · ~3m · writes: trend_history table, in-memory preflight payload

This phase used to be a Haiku call. It is now zero LLM. preflight/run_all.py runs eight source modules concurrently on an 8-worker thread pool, then preflight/trends.py clusters the items by embedding similarity and scores clusters on engagement and source diversity. Deterministic, so a resumed run can re-run it for free.

Python then embeds every item and compares it against ten days of stored findings. 03ResearchPhase.RESEARCH◆ 13–26 Claude processes

critical · ~20m · writes: findings, findings_embeddings, sources, agent_runs

Thirteen parallel Claude processes with a JSON contract each. Detailed in the next section.

04SynthesisPhase.SYNTHESIS◆ 2 Opus passes

critical · ~7m · writes: reports/ramsay/YYYY-MM-DD.md

Pass 1, story selection. Model claude-opus-5[1m], system prompt agents/synthesis-selector.md, max 10 turns, 600s timeout. Input is the day's findings after a source-balance rebalance, each one carrying an inline "already covered on {date}" marker keyed on its source URL against 30 days of published issues, plus user preference weights, trend topics, and a formatted block of the last 21 days of published stories. Output is exactly 5 stories with reasons.

A deterministic republish tripwire then compares the selection against the published archive by stemmed word-overlap. A repeat forces one re-pick with the offending titles named. If the second attempt still repeats, the issue publishes anyway and a Slack alert fires. Never a silent repeat, and never a blocked newsletter.

Pass 2, writing. Same model, system prompt agents/synthesis-writer.md, max 30 turns, 900s timeout. The prompt opens with an output contract: stdout is published verbatim, so emit only newsletter markdown, and never mention tools, sessions, finding counts, dedup or coverage constraints. All findings, soul.md, voice.md, narrative arcs, the published-history block and recent failure lessons go in. Three attempts. If all three fail, Python builds a deterministic source-list brief from stored findings and alerts loudly rather than shipping nothing.

Post-processing is all Python: strip any process narration before the first heading, replace the model's H1 with a deterministic # {title} — {date}, run the prose gate, write the file, run the URL republish tripwire, score the issue on six dimensions, and assess the quality floor.

The quality floor never rewrites the issue

It used to. On 13 July 2026 a thin research corpus tripped the floor and a finished newsletter was replaced by a bare fallback list. Now the floor only reports. It writes to traces and alerts Slack, and the issue the writer produced goes out untouched.

05DeliverPhase.DELIVER■ Python only

skippable · ~1s · writes: the email, receipts row, ran-marker file

orchestrator/newsletter.py validates the report, appends a feedback footer, converts markdown to HTML with markdown2, and posts to the Resend API with both HTML and plain-text bodies, retrying with backoff. Subscribers get a separate broadcast from the pre-footer copy.

A receipts table handles idempotency. The deliver phase claims the key newsletter:{date} before it sends, so a crash-and-resume cannot double-send. And the day's "done" marker in /tmp is written only on confirmed delivery, which is the reason the hourly retry windows are safe to run.

Why the marker moved

On 13 June 2026 the shell wrapper touched the done-marker before running the pipeline. The pipeline crashed at startup. The marker said the day was finished, so every retry window skipped, and no newsletter went out all day. A one-second bug became a full-day outage. The marker now belongs to the deliver phase alone.

06Site contentPhase.SITE_CONTENT■ Deterministic core◆ writer + critic

skippable, fails open · ~2h47m · writes: reports/ramsay/site-*/ artifacts, kg_* tables

Builds the public site, Rabbit Hole. orchestrator/site_content_engine.py reads a public-safe corpus model over memory.db, picks candidates, assembles a graph pack of evidence per story, runs an expert loop, and generates the story. The live writer (agents/site-story-writer.md) and desk critic (agents/site-story-critic.md) are optional and fail closed to deterministic copy. If the model is unavailable, or its draft fails site_copy_lint.py, the deterministic version ships. Entity and source dossiers follow, then an opt-in knowledge-graph extraction over the day's findings.

07LearnPhase.LEARN■ Python◆ 1 Sonnet call

skippable · ~24s · writes: run_quality, validated_patterns, entity_graph, data/ramsay/learnings.md

Scores the run, compares against the 7-day average and stores a failure lesson on a drop. Attributes quality changes to prompt files edited since the last run and flags regressions. Extracts entity relationships from high-importance findings. Backfills which trends actually produced findings. Then runs the three memory lifecycle operations: consolidate() clusters agent notes into validated patterns at 0.80 similarity, promote() elevates patterns seen by 2+ agents with 3+ observations (or 5+ from one), and prune() archives stale notes and patterns. Finally one Sonnet call regenerates learnings.md, with a deterministic fallback if it fails.

Caveat, and I checked this rather than assuming it. The three lifecycle calls are currently no-ops. Nothing in the daily pipeline writes agent_notes, the table consolidate reads from, so it has zero rows. The only production caller of store_note() is the Slack follow-up service. The 223 rows in validated_patterns were all created between 3 March and 9 April 2026 and have not moved since. Scoring, regression detection and failure lessons in this phase are live and working. The pattern-learning half is wired but starved.

08SocialPhase.SOCIAL◆ ~8 sequential agents

skippable, off by default in launchd · writes: social_posts, data/social-drafts/*

social/pipeline.py replaced 1,259 lines of bash. Eleven steps: post any deferred drafts, check rate limits before spending any tokens, EIC picks the topic on Opus with up to 3 retries, human approval gate 1 in Slack, creative brief, optional art pipeline, per-platform writers in parallel, blind critics in up to 3 rounds, deterministic policy validation, humanizer, expeditor as the final quality firewall, approval gate 2 in Slack, then posting with random jitter inside a configured window. If the EIC finds nothing worth publishing it declares a kill day and the phase ends with no post.

09EngagementPhase.ENGAGEMENT◆ finder + writer

skippable · writes: engagements table

Finds the top conversations worth replying to based on the day's research, drafts substantive replies, routes them through the same Slack approval gateway, then posts and follows. A receipt on follow:{platform}:{handle} guards every follow.

10IdentityPhase.IDENTITY◆ 1 Sonnet call

skippable · writes: data/ramsay/mindpattern/{soul,user,voice,decisions}.md

The system edits its own identity files. It assembles a summary of the day (findings count, newsletter scores, which topic the EIC chose, how the human ruled at each gate) and asks the model for a JSON diff over four files. memory/identity_evolve.py applies it with size limits and validation. Those same files are loaded back into every research agent prompt and both synthesis passes the next morning, and that is where the loop closes.

What actually changes, measured against the last commit: decisions.md gains a substantive dated entry every run and is read back seven entries at a time. soul.md changes in exactly one section, a running commentary on run statistics; its values and personality sections are static. voice.md has not changed a single line since 26 June, and user.md not since 1 July. Since the scheduled run passes --skip-social, four of the eight inputs to this prompt (topic, both gates, expeditor) arrive as "not available" every day. So the phase writes real analysis into a journal it reads back, but it is not currently changing how the system writes.

11MirrorPhase.MIRROR■ Python only

skippable · ~2s · writes: Obsidian vault markdown

Regenerates the SQLite contents as browsable markdown in the Obsidian vault: daily notes, per-source pages (2,400+ of them), topics, people, newsletters. SQLite stays the source of truth. The vault is a second copy you can open in Obsidian and read by hand.

12SyncPhase.SYNC■ Python only

skippable · ~3m · writes: Fly volume, synced-marker

Tars memory.db plus the day's reports into one bundle and uploads it over flyctl sftp, one connection instead of thirty. Then restarts the Fly app so the dashboard reopens the replaced database file, waits for its warm-up, and serially requests the day's new pages so Vercel's CDN copy exists before the first reader arrives. A failed sync alerts Slack with the count of unsynced local issues.

05Research, in depth

One phase, thirteen Claude processes, one JSON contract each. This is the part interviewers usually want walked through slowly.

Why thirteen, and why they are not subagents

The count is thirteen, one markdown skill file per agent in verticals/ai-tech/agents/. They are not Claude subagents inside one session. Each is a separate claude -p OS process with its own context window, its own tool budget and its own 30-minute timeout. Python owns the fan-out via a ThreadPoolExecutor with max_workers=6, so six run at a time and the rest queue.

Six rather than thirteen is a deliberate throttle. When all thirteen hit rate limits simultaneously the retries themselves become the overload, which is why the backoff uses full jitter, uniform(0, min(cap, base * 2**attempt)), rather than a fixed delay. Jitter desynchronizes the wave.

What goes into a single agent prompt

build_agent_prompt() assembles roughly nine blocks in a fixed order, with the output contract stated at both the top and the bottom because instruction-following degrades in the middle of a long prompt:

  1. The JSON schema and the words "output ONLY valid JSON"
  2. verticals/ai-tech/SOUL.md, overridden by the vault's soul.md when present
  3. data/ramsay/mindpattern/user.md
  4. The agent's own skill file, 65 to 162 lines of domain, sources and quality bar
  5. Memory context from memory.get_context(): this agent's findings from the last 7 days, its top sources, today's findings from other agents with semantic overlap flagged, its self-improvement notes (always empty, see phase 7), and cross-agent validated patterns (a frozen April 2026 snapshot)
  6. Today's detected trends
  7. Phase 1, the preflight items routed to this agent, with already-covered ones struck through and dated
  8. Phase 2, explicit instructions for going beyond preflight (Exa, WebFetch, Jina, twitter CLI, yt-dlp, WebSearch)
  9. The novelty requirement, research methodology, and a mandatory six-point self-critique gate the agent must apply before emitting anything

The self-critique gate does the most work. Before emitting anything the agent must drop any finding whose primary source is older than 48 hours, any topic covered in the last 10 days without new data, and any rewrite that adds no information. Anything it can only single-source gets downgraded to low importance rather than dropped.

Parsing what comes back

Models emit JSON imperfectly, so _parse_findings() tries four strategies in order: direct json.loads, then a character-by-character balanced-brace scanner that tracks string state so braces inside values do not confuse it, then a balanced-bracket scan for a bare array, then a warning with the first 200 characters logged for forensics.

Failure classification

The CLI writes API errors to stdout, sometimes with exit code 0, so classify_agent_failure() inspects both streams and returns one of five classes:

Above that, the phase does one corrective re-dispatch of any agent that finished with an error and no findings, because a transient cause (a server-error burst, a sleep window) has usually passed by the time the first wave finishes.

Why the re-dispatch exists

On 19 August 2026 the Mac was on battery and slept mid-run. Twelve of thirteen agents died mid-response and a 12-finding issue shipped. Software cannot stop that sleep, so two things changed: a battery warning fires at INIT while it can still help, and failed agents get one automatic second pass.

What survives into storage

Findings do not go straight into the database. In order: cross-agent semantic dedup at 0.85 keeping the higher-quality copy of each pair, then the policy engine (required fields, valid importance value, URL sanity, banned entities, eight prompt-injection regexes) rejecting bad findings before storage, then a stale-source gate on any URL whose own path encodes a date more than 30 days old, then a semantic near-duplicate check at 0.90 against 180 days of history. On 20 August 2026, 189 findings survived all four from 13 agents. If zero survive, the phase raises and the run fails, because a newsletter with no research is worse than no newsletter.

Embeddings run locally

memory/embeddings.py loads BAAI/bge-small-en-v1.5 through fastembed once at import, 384 dimensions, vectors already normalized so cosine similarity is a plain dot product. Similarity search is a numpy matrix multiply against a column of stored blobs. Nothing in this pipeline calls an embedding API, ever. The ONNX cache is pinned to ~/.cache/mindpattern/fastembed because macOS purges /var/folders and a dangling symlink there silently broke the research phase once.

How much of that schema is actually alive

61 tables sounds like more system than it is, so I counted. In memory.db, 14 tables get written every run and another 5 on event. Eight are frozen: validated_patterns stopped 9 April, patterns 11 March, signals 13 July, social_metrics 5 March. Five have never held a row at all: agent_notes, agent_checks, claimed_topics, editorial_corrections and the notes embedding table. There is also a findings_fts full-text index that was created over the findings table and never populated, so a MATCH query returns nothing. No code queries it, so it is dead weight rather than a broken feature.

traces.db is worse. Nine of its 18 tables are empty, and three of those nine are superseded duplicates of tables that are live: prompt_versions against prompt_tracker, pipeline_phases against phase_tracking, quality_scores against quality_history. traces_db.py still creates the old names on every open while observability.py and prompt_tracker.py write the new ones. Checkpoint and resume

Every completed phase writes a checkpoint row to traces.db. On start, run() looks for a resumable run for today and, if found, adopts its identity rather than creating a new one, so a single logical execution never splits across two run IDs. A resume targeting RESEARCH deliberately rewinds one step to TREND_SCAN, because preflight items are not checkpointed and research without them runs in a degraded mode.

Why layer 5 had to be added

Layers 1 to 4 all compare findings. None of them ever looked at what past issues actually published. A 17 August 2026 audit found 26 stories re-reported as new across 20 issues while every gate scored green. orchestrator/published_history.py reads the published markdown itself. It is deliberately embedding-free, so the hard check keeps working in tests and when the model misbehaves.

Six-dimension scoring

orchestrator/evaluator.py is entirely deterministic. It scores coverage 0.25, dedup 0.20, sources 0.15, actionability 0.15, topic balance 0.15 and length 0.10 into a composite. assess_quality_floor() then compares against roughly twenty thresholds (minimum 11 of 13 agents active, minimum 70 findings, at least 4 source classes, top-domain concentration under 0.35, 75% source responsiveness) and returns pass, degraded, or fail_retryable. All three publish. Only the reporting changes.

Those thresholds come from measured runs, not from guesses. The old concentration ceiling gated the raw candidate pool, which RSS dominates purely because feeds are verbose, and it breached on all 29 logged days. It now measures findings that reached the newsletter, where the healthy observed range is 0.14 to 0.30.

The policy engine

policies/research.json is data, not code: required fields, allowed importance values, maximum findings per agent, maximum summary length, a 48-hour age limit, banned entities, and eight named prompt-injection regexes covering instruction override, role reassignment, system-prompt exfiltration and role-play commands. Preflight explicitly does not filter injection text out of scraped content. This engine is the one place that checks it, after the agent has seen it and before it enters memory.

10How it fails

Two phases are critical. Everything else degrades. The design principle: publish something honest, alert loudly, never publish silently wrong.

  • RESEARCH or SYNTHESIS fails → run marked FAILED, Slack alert, exit 1, no marker written, next retry window picks it up.
  • Any other phase fails → caught, logged, appended to warnings, run continues and finishes as completed with the warnings recorded.
  • Story selection fails 3 times → Python builds a deterministic Top 5 from stored findings by importance and source quality, and the prompt tells the writer it is in recovery mode.
  • The writer fails 3 times → Python publishes a deterministic source-list brief and an urgent Slack alert names the reason.
  • Delivery fails → the run finishes as completed_degraded with exit code 1, so status, exit code and the missing marker all tell the same story instead of a false success.
  • Sync fails after delivery → the next window runs --sync-only, never a full rerun. A full rerun would double the day's findings and rewrite a published issue, which is exactly what happened on 14 July 2026.

Concurrency and idempotency

Three independent guards: an flock in run.py, an atomic mkdir lock with stale-PID reclaim in run-launchd.sh, and a receipts table claimed before every irreversible outbound action. The wrapper can fire twenty times a morning and at most one pipeline runs.

11The harness that edits the code

A second loop, outside the daily pipeline, where agents find issues in the repository, plan fixes, write tests first, and open pull requests. It shipped 16 merged PRs, then went dormant in April and has not run since.

harness/ applies the same deterministic-versus-agentic split one level up. Deterministic: ticket schema validation, security-sensitivity detection by path match, review-depth routing, pytest execution, ast.parse syntax checks, regex secret scanning, debug-statement detection, diff scope checking against the ticket's declared files, ticket lifecycle, and knowledge-graph validation. Agentic: scouting for issues, architecture planning, threat modelling, writing the fix, and reviewing it.

The flow is a ticket, then a plan agent in its own git worktree, then a fix agent doing TDD in a branch, then five deterministic gates that must all pass, then a review agent in a separate worktree. That review runs three specialist subagents in parallel, testing, security and maintainability, and they compute a score. Seven or above passes, pushes the branch, and opens a PR with the evidence attached. GitHub Actions runs pytest as the final hard gate. A human merges or closes, and the harness writes that decision back to harness/feedback.json so the scout learns what gets accepted.

Track record, checked not assumed

34 tickets exist, all created between 31 March and 2 April 2026. Their end states: 3 done, 12 failed, 4 stuck in progress, 15 never picked up. Sixteen pull requests came off harness/* branches and all sixteen merged, between 1 and 3 April. Nothing since. harness/audit.jsonl holds one line, dated 7 May. harness/feedback.json is an empty array, so the merge-decision loop that was supposed to teach the scout has never had a single data point. There is no launchd job for it; bash harness/run.sh is a manual invocation and nobody has invoked it in four months.

Claude Code hooks enforce it at the tool level. A PreToolUse hook blocks git commit inside harness worktrees when it finds syntax errors, secrets or debug statements. A PostToolUse hook appends every tool call to harness/audit.jsonl. A third validates the knowledge graph after Python edits.

The knowledge graph itself is 31 hand-written markdown files linked with [[slug]] wiki-links, supporting section-level references like [[orchestrator/runner#Error Handling]], with a stack-based section parser, a suffix index, a five-tier fuzzy search, four validation passes, and bidirectional links back into Python source through # @know: comments.

12Where it runs

The Mac does the work

A launchd agent, deploy/com.mindpattern.pipeline.plist, fires run-launchd.sh every 15 minutes from 05:00 to 09:45. Twenty triggers, and nineteen of them are no-ops. The wrapper enforces a 05:00–09:59 window, checks the delivery and sync markers, takes an atomic lock, fast-forwards main, holds caffeinate -i -s for the duration, and runs run.py --skip-social.

Dense triggers exist because of a real timezone problem. Powerd and launchd's calendar scheduler both drifted onto Pacific while the machine was elsewhere, and on battery macOS skips the scheduled wake entirely. Fifteen-minute spacing means the run starts within a quarter hour of the first manual wake rather than waiting for the next hour.

Fly.io hosts the front

One shared-cpu-2x machine, 2GB, region sjc, with a persistent volume at /data. start.sh runs two processes under tini: a uvicorn server for the FastAPI dashboard on port 8080, and the Slack Socket Mode bot. Either dying exits nonzero so Fly restarts the machine. Secrets are Fly env vars in the container and macOS Keychain locally.

The dashboard mounts 18 routers: newsletters, findings, skills, traces, run history, prompts, metrics, performance, pipeline status, site search, site analytics, social and engagement history, an editor's desk, an SSE stream and a sync upload endpoint. mindpattern.ai is the public face, served through Vercel with the Fly app as its backend.

Slack is the control surface

The bot runs channel-based handlers for approvals, posts, tips, skills, briefings, engagement, follow-ups and harness commands. Approval gates block the social pipeline until a human answers, and gate 1 accepts a custom topic that replaces the EIC's choice entirely. Harness commands stay Mac-only.

14Answers you will need

Is this agentic, or is it a workflow?

Both, at different levels. The outer loop is a hard-coded state machine with no model in the control path. The inner work is genuinely agentic: each research agent runs up to 35 turns, decides which tools to use, follows leads, and applies its own critique gate before answering. Agency stops at the phase boundary.

Which model, and how do you pay for it?

The Claude CLI in headless mode against a personal Anthropic subscription. Research agents and both synthesis passes run on Opus, with the 1M-context variant where the whole day's findings have to fit in one window. Sonnet handles bounded writing and review. Nothing calls the paid API, and there is no API key in the project.

What stops it hallucinating a newsletter?

Four things in sequence. The system prompt says the finding count is a description, not a quota, and that fewer real findings is always correct. The policy engine rejects findings missing a source URL before storage. The stale-source and 180-day similarity gates drop recycled news. And the six-dimension evaluator scores source density in the published text. If the model refuses rather than fabricates, that is the outcome I designed for, and the pipeline records it.

Why thirteen agents rather than one big prompt?

Three reasons. Context isolation, so a paper-heavy day cannot crowd out the security beat. Failure isolation, so one agent timing out costs one thirteenth of the day rather than everything. And prompt specificity, since each skill file names actual sources, people, subreddits and quality bars for its beat, which a single prompt cannot do at that depth.

What was the hardest part?

Everything about non-determinism at the seams. The model refusing in prose where a parser expected JSON. The same prompt producing 42 em-dashes one day and 2 the next. A tool grant that named a binary nobody had installed. The pattern in every fix is the same: move the check out of the prompt and into code, at the point where the failure would actually do damage.

How does it improve itself?

Three loops are built. One of them is running. I would rather say that in the room than get caught on it.

Working: the daily quality loop. Every run is scored on six dimensions, compared against the 7-day average, and a drop writes a failure lesson. Prompt file hashes let the next run attribute a quality change to a specific prompt edit. That produces a real 175-run series, and the 19 August collapse from 0.719 to 0.573 showed up in it the same day.

Half-working: identity. It writes genuine daily analysis into decisions.md and reads the last seven entries back. But voice.md, the file that actually shapes the prose, has not changed since June, so the loop turns without moving anything.

Dormant: pattern consolidation and the harness. Consolidation reads a table nothing writes. The harness merged 16 PRs in April and has not been run since. Both are wired end to end and both would work if I fed them, which is a different problem from being broken, but it is not the same as running.

What would you build differently?

The site content phase takes 2 hours 47 minutes and sits inside the same sequential run as everything else. It should be a separate job triggered after delivery. And thirteen agents at six-way concurrency is tuned for one machine's rate limits, not for throughput. The fan-out width is a config value I have never gone back and revisited.
