    Lesson 01 · Start here · Your role

    Know what you are directing

    Build a small vocabulary you can use to ask an agent for work and judge its answer.

    You will build a development brief and an evidence checklist for a story-search improvement. By the final lesson, you will have a reusable prompt sequence in your notebook. You can take that sequence into an agent conversation and supervise a small task.

    This course uses an invented search problem: a reader remembers part of a published story's title and wants to find it. It is a teaching example, not a report of a current MindPattern bug. The browser exercises run sample JavaScript. They do not launch agents or change your application.

    Identify the people and tools

    1. You define the outcome. For example, a reader types part of a title and finds the right published story. You decide whether that solves a worthwhile problem.
    2. The agent investigates and implements. It can inspect files, propose designs, edit code, and run tools when its environment allows those actions.
    3. A skill supplies reusable instructions. A skill can tell the agent how to verify search. Reading those instructions does not itself run a check.
    4. A tool performs an action. A command-line interface, or CLI, is a program you operate with text commands. A browser driver can type into a page and inspect the result.
    5. Evidence records what happened. A returned story, a failing assertion, or a screenshot can support a particular claim.

    Complete the question below. Then describe one responsibility you want to retain and one you want the agent to handle.

    What is pstack doing?

    pstack is a collection of agent skills and workflows. Its poteto-mode skill reads the kind of task and routes to relevant instructions. A playbook is one of those task-specific workflows. A subagent is a separately assigned agent with its own task context. None of these names guarantees correctness. Their value comes from the actions they cause and the evidence those actions produce.

    How the references fit

    Lauren's Part 1 puts verification at the foundation: an agent needs a repeatable way to operate an app and check the result. Part 2 adds research, design exploration, and execution planning. Shopify describes a migration process with small checkpoints and review. This course combines those ideas into original exercises. It does not claim to reproduce Shopify's internal system.

    Lesson 02 · Practice · Define the outcome

    Turn an idea into a clear request

    Write a brief that leaves implementation open while making success observable.

    Start with this vague request: Make search better. An agent could reasonably change ranking, appearance, speed, spelling correction, or the search button. You need to narrow the outcome before choosing code.

    Build the request

    1. Name the reader's action. A reader types a remembered word from a story title.
    2. Name the expected result. A matching published story appears. A draft story never appears.
    3. Add relevant constraints. Preserve the public response shape. Work with synthetic data first. Leave live publishing alone.
    4. State the evidence. Show the query, returned titles, an absent-query case, and a draft-exclusion case. If the visible search page changes, show that interaction too.

    Use the brief builder below. Replace at least one example field with your own words. Read the generated prompt as if you were the agent receiving it.

    You should now be able to say what a correct result looks like without selecting a search library or prescribing the implementation.

    How much detail should you provide?

    Give the agent facts it cannot infer reliably: who the feature serves, the experience you want, boundaries, and the tradeoffs that matter to you. Let it discover file paths, existing functions, and current behavior. If you insist on a specific implementation too early, the agent may optimize your proposal instead of investigating the underlying problem.

    Use a restatement as a comprehension check

    Ask the agent to explain the problem in its own words before a substantial change. Read for omissions. If it says 'improve ranking' but your concern is draft exposure, correct that misunderstanding immediately. A clear restatement is still a hypothesis about your intent; it becomes useful when you compare it against what you actually meant.

    Lesson 03 · Part 2 · how, why, teach, recall

    Make the agent understand the current system

    Separate observed behavior, historical explanations, and assumptions before approving a design.

    The agent now understands your request. It still needs to understand the application. Give it a small investigation with a concrete deliverable: trace one search query from the reader's action to the returned story.

    Inspect the investigation

    1. Ask how to trace the current route. Look for the entry point, the function that selects results, and the result returned to the caller.
    2. Ask why when a design constraint needs historical explanation. Look for a commit, issue, or document that supports the explanation.
    3. Ask teach for a plain-language account you can challenge. Ask where that account is uncertain.
    4. Use recall when relevant work happened in an earlier conversation. Compare recalled context with current files before relying on it.

    Practice with this invented report: The API returns the expected story for the title query. The browser still shows an empty list. The response field was probably renamed last month. The first two sentences describe observations if the agent actually ran those checks. The third sentence is a hypothesis until source or history supports it.

    Write a follow-up that asks the agent to trace how the browser reads the response. You should not need to choose a fix yet.

    What counts as grounding?

    A list of filenames is a starting point. Useful grounding connects behavior across those files. For this example, it explains which browser action starts a request, how the backend selects published stories, and which response fields the browser renders. Ask for the specific condition that would explain the mismatch and a check that could disprove it.

    What if history is unavailable?

    The agent can often explain current mechanics from source even when it cannot establish original intent. A truthful answer says that the current code does X and that the reason for choosing X is unknown. Do not reward a plausible story as if it were historical evidence. Connected issue trackers or chat services are optional evidence sources; a skill does not create access to them.

    Try this with your agent

    These are course-authored prompts. Use the skill names as instructions to your coding agent, not as terminal commands.

    Use how to trace a title search from user input to displayed results. Use why only for design decisions whose history matters. Use teach to explain the path in plain language. Separate observations, source-backed explanations, and hypotheses. Cite the relevant files. Keep this read-only.

    What to look for

    You can explain the request path back to the agent. Any claimed reason for an old decision has a source or an explicit uncertainty.

    Common mistake. Accepting a fluent explanation that never identifies the behavior or evidence it describes.

    The agent says the old ranking rule exists 'for performance' but provides no history or measurement. How should you treat that?

    Lesson 04 · Part 1 · The verification toolkit

    Connect the skill, CLI, and feature map

    Follow one feature from its instructions to the command and the evidence it produces.

    These three pieces answer different questions. A verification skill tells the agent how to check the application. The CLI lets it perform repeatable actions. The feature map tells it which behavior to inspect and how to reach it.

    Follow the MindPattern example

    1. Locate .agents/skills/verify-mindpattern/SKILL.md. Its launch, doctor, drive, evidence, and cleanup instructions describe the checking procedure.
    2. Locate .agents/skills/verify-mindpattern/references/features/README.md. Its index links to a story-search entry.
    3. Read the story-search entry before choosing a command. Find the expected matching, absent, and excluded results.
    4. Find the CLI under verification/. The command .venv/bin/python3 -m verification verify story-search runs the named scenario.

    The browser course cannot read your checkout through these paths. Use the prompt below in your agent conversation to inspect the actual files. The files are already present in this workspace.

    For a different application, the same roles might be filled by a simulator driver, a browser controller, or a library example runner. Copying MindPattern's commands into that application would not create a working verification system.

    What does create-verification-skill create?

    The installed generator instructs an agent to inspect the repository, identify how to start and drive the app, write a project-specific skill, seed a feature map, and execute its instructions. A useful output contains real commands and expected observations. A document with placeholders is a draft. The generator is reusable; verify-mindpattern is its app-specific counterpart.

    Why have a CLI at all?

    A repeated command reduces setup variation. Compare asking each agent to invent a fresh script for search with giving each agent one maintained command. Repetition makes failures easier to compare. The command still needs to use a meaningful application path. A tool that prints a canned success message is reproducible without being useful.

    Lesson 05 · MindPattern · Optional real CLI exercise

    Run a check and read the evidence

    Make a precise claim about one executed scenario instead of treating a pass as proof of the whole product.

    This is an optional exercise in your real repository. The commands below already exist. Run them from /Users/taylerramsay/Projects/mindpattern-v3, or ask your coding agent to run them there. The tutorial page itself does not execute them.

    Follow the evidence

    1. Read .venv/bin/python3 -m verification --help. Identify the available commands before using them.
    2. Run .venv/bin/python3 -m verification doctor. Read which instance it describes. This is a synthetic instance, not production health.
    3. Run .venv/bin/python3 -m verification features story-search. Confirm that the feature and its limits match the task.
    4. Run .venv/bin/python3 -m verification verify story-search. This creates a new evidence directory automatically.
    5. Open manifest.json in the exact evidence directory returned by that command. Read the assertions and observed responses, then check that the file still exists after runtime cleanup.

    If the command fails, record the exact failure and inspect its evidence. Do not paste an expected success result into the notebook as if you observed it. If you skip the real exercise, write not run.

    The current driver copies current source into a temporary workspace and supplies synthetic artifacts. Its default requests exercise the actual FastAPI app through ASGI, an interface that connects requests to Python application code. The run skips application startup lifespan work, including background warmup.

    Choose the level that matches the claim

    An API response check can show which stories the backend returned. Starting the CLI's serve mode and using its explicit loopback HTTP request mode adds real HTTP observation. Neither proves what a browser displays. A rendered search change also needs browser interaction. A real research run has different provider and data concerns. Match the evidence to the claim instead of arranging these checks into a universal score.

    What is verified today?

    The toolkit currently provides five scenarios: stories, story-search, site-artifacts, sitemap, and private-access. The recorded toolkit verification passed 36 assertions, and the associated focused test run passed 35 tests. Those are historical development results, not a fresh run from this course. Browser rendering, the full pipeline, live providers, and startup warmup are outside that evidence.

    Keep the test fixture in mind

    A fixture is a known set of sample inputs. Synthetic data makes a check repeatable and avoids mixing the exercise with personal research state. It can prove how the code handles those inputs. It cannot establish that the real corpus is complete or editorially good. Changing the input coverage can change what a successful check means.

    Lesson 06 · Lauren's reply · Observe, diagnose, fix the skill

    Catch a green check that misses the problem

    Expose a weak check, then repair the simulated behavior and rerun a check that can detect the defect.

    In the reply you shared, Lauren's answer to a green verification result with a wrong product was: observe, diagnose, fix the skill. Practice that response here.

    The lab starts with an invented response that exposes a draft alongside published stories. A status-only check can pass because the response succeeds technically. The reader outcome is still wrong.

    Make the check earn its result

    1. Run only the status check. Predict whether it will pass before pressing the button.
    2. Inspect the returned stories. Find the draft that the status check ignores.
    3. Select the draft-exclusion check and rerun. Keep the simulated application unchanged. The new check should expose the defect.
    4. Repair the simulated filter. Run the stronger checks again and inspect which stories remain.
    5. Explain why the second green result supports a stronger claim than the first.

    This is deliberately broken teaching code. It is not a diagnosis of MindPattern's current implementation. Its purpose is to let you observe the difference between a weak success criterion and a useful one.

    Separate the product defect from the verification defect

    The product defect is the draft appearing in public results. The verification defect is a check that never asks whether drafts appear. Fixing only the product leaves the same blind spot available for a later regression. Fixing only the check reveals the problem without making the product correct. A complete repair addresses both, at the right layer.

    A useful regression check must be able to fail

    After observing a defect, add a check that disagrees with the known wrong behavior. In this lab, the disagreement is that a draft is present when none should be present. A crash from a typo in the checker would also produce a failure, but it would not prove the checker detects draft exposure. Read the failure, not only its color.

    When the checker is wrong

    Sometimes the application behavior is correct and an outdated expectation is wrong. Compare the expected result with the agreed user outcome and current product contract. Do not change an expectation merely to make a report green. Record why the new expectation is the intended behavior.

    Write an entry for the story-search outcome. Imagine a new agent opens it with no access to your conversation. It needs enough detail to reach the feature, operate it, and recognize both success and a misleading result.

    Draft the entry in your notebook

    3. Give the drive command. For the existing backend check, name verify story-search with the repository interpreter prefix.

    Why an endpoint inventory is insufficient

    A list of routes describes addresses the software exposes. A feature entry describes a useful behavior. One reader journey can cross several routes, require authentication, create state, and survive a reload. Conversely, several routes can support one feature. Start from the user action and follow the behavior through the software.

    Keep useful knowledge close to the work

    A feature map saves the next agent from rediscovering the same entry points and constraints. That only helps while the map is accurate. When a command changes, update its usage. When an interaction changes, update its expected result. Keep unverified workflows visible instead of counting every documented item as automated coverage.

    Our current map has five runnable backend scenarios and a separate inventory of other workflows. That is a starting set. Adding a browser description alone does not add a browser driver. A complete entry must distinguish instructions that a tool can execute now from an unimplemented verification method.

    Lesson 08 · Part 2 · Planning through code

    Try alternatives before choosing a design

    Use two working sketches to make one specific product decision.

    You have an outcome and a way to observe it. Now explore a design question: should a title query require the whole title, or match a remembered part? The lab implements both behaviors over the same invented stories.

    Compare the behavior

    1. Enter part of a displayed story title. Compare the two result panels.
    2. Enter the complete title. Check whether both approaches find it.
    3. Change capitalization. Observe what each implementation actually does.
    4. Clear the query. Decide what you want an empty search to mean.
    5. Write which approach better serves the remembered-title task and which limitation remains.

    You have now used executable examples to answer a design question. The lab is an original teaching sketch. Its tiny data set does not measure production search quality or speed.

    In a real task, ask the agent to create alternatives that test a meaningful uncertainty. Give each alternative the same inputs. Require the agent to show the result and explain which tradeoff matters. Keep the prototypes separate from production code until you choose a direction.

    What makes a useful prototype?

    Name the decision before building. 'Find out whether partial-title matching serves this remembered-title task' is a decision. 'Build something impressive' is not. A small script can answer a backend behavior question. A browser sketch can answer an interaction question. A benchmark needs a representative workload and actual measurements. Do not infer timing from a screenshot or infer visual usability from an API response.

    Lauren's planning clarification

    In the replies you supplied, Lauren describes using architect and prototyping to produce options, then turning a choice into a plan. She also says she does not use native Plan mode. That is a preference about how she develops evidence, not a ban on planning. An execution plan becomes more useful after the important design uncertainties have been tested.

    Avoid polishing an unanswered question

    A prototype can have rough styling and disposable code while still producing useful evidence. Spend effort on the uncertain behavior. If the experiment disproves an assumption, change or discard the approach. A polished implementation of the wrong assumption makes the later correction more expensive.

    Lesson 09 · Part 2 · Shape the code around its use

    Understand what architect adds

    Review a small interface sketch without needing to dictate every line of implementation.

    A prototype helped choose behavior. Architecture decides how production code will own that behavior. For this exercise, ask where search should receive stories, select results, and enforce publication rules.

    Read a caller's sketch

    request = SearchRequest(query="agents", limit=10)
results = search_published_stories(request, story_repository)

    This is illustrative pseudocode, not an existing MindPattern API. A caller's sketch shows how another part of the program would use the proposed code. A type describes the shape of a value. A function signature names the inputs and result without supplying its implementation.

    1. Ask what the caller needs to know. It should not have to understand several hidden initialization steps to issue one search.
    2. Ask who owns publication eligibility. If every caller must remember to remove drafts, a new caller can forget.
    3. Ask what happens for no matches, invalid limits, and unavailable data. Distinguish a normal empty result from an operational failure.
    4. Compare a second design using the same caller scenario. Ask what complexity each interface hides and what it exposes.
    5. Choose the shape that fits the existing system and makes the required behavior easier to preserve.

    You do not need to identify every future edge case. You need to understand the important ownership decisions and see how the proposal handles today's evidence.

    How architect differs from prototyping

    Prototyping tests a question through an executable sketch. Architect develops the structure of an implementation: caller usage, data types, function boundaries, alternatives, and rationale. The installed skill asks for independent design candidates and synthesis. The two workflows can inform each other. A sketch that becomes awkward when exercised is evidence that the proposed structure needs revision.

    What you should challenge

    Ask concrete questions: Where is the draft rule enforced? Can an empty result be confused with a timeout? What changes for the existing caller? A long list of hypothetical disasters rarely helps. Challenge a design using a plausible caller or observed failure. If the agent needs several exceptions to handle that case, ask whether ownership is misplaced.

    Why explicitly name architect?

    Lauren's pasted clarification says her explicit skill invocation illustrated what poteto-mode can do behind the scenes. You can name architect when you want to make the design step unmistakable. You do not need to paste every available skill into every prompt. The installed workflow and your task should determine which ones apply.

    Lesson 10 · Part 2 · Execution planning

    Turn the chosen design into small proofs

    Write a plan in which each task ends with an observable result.

    The design is now concrete enough to execute. Make the plan describe useful increments. You should be able to inspect each increment before it becomes part of a larger change.

    Draft three checkpoints for the example

    1. Establish the intended search behavior. Use synthetic published and draft stories. Record the current result for a title fragment and the intended result.
    2. Implement the selected backend behavior. Preserve response contracts. Verify matches, absent terms, case handling, and draft exclusion through the request path.
    3. Integrate and inspect the reader interaction if it changes. Enter the query in the real browser interface, inspect returned stories, and verify its empty state. Preserve appropriate evidence.

    For each checkpoint, write the outcome, affected scope, verification method, evidence artifact, and reason it would fail. Adjust the split to fit the actual source after investigation. These are example checkpoints, not a command to change the current application.

    A task called implement frontend leaves you guessing what you can review. A task called enter a title fragment and show the matching story in the search page gives you a result to inspect.

    What a plan should leave open

    The chosen design constrains the main boundaries. Implementation may still reveal details that the sketch missed. Let the agent resolve routine details and report meaningful deviations. If the same workaround appears repeatedly, return to the design instead of extending the plan around it indefinitely.

    Why green tests are one part of a checkpoint

    A focused test can establish a regression condition. A runtime check can show that the changed integration path behaves as intended. Browser inspection can show what the reader sees. Choose the evidence required by the change. A backend-only internal change does not automatically need a new screenshot; a rendered interaction cannot be judged solely by its backend test.

    Where to keep plans and decisions

    Lauren's pasted reply discourages keeping permanent planning material unless it helps future decisions. Your repository agreements require a durable handoff for long work. Keep the active task's status and necessary operating context there. Review temporary planning material when work ends. Do not delete existing runbooks or decision records merely because another developer prefers a different storage habit.

    Lesson 11 · Shopify · The Helix contribution

    Review the running result and the code

    Decide whether a checkpoint has enough evidence to advance.

    Shopify describes Helix proposing small ordered checkpoints from an existing screen. Each checkpoint passes tests, a running-app visual review, two adversarial code reviews, and human review before a commit. Feedback informs later work. Shopify also describes a CLI for headless business logic and a remote mode for driving simulator UI. This course teaches those published ideas; it does not provide Helix's internal implementation.

    Review this invented search checkpoint

    The agent reports: Backend checks pass. A browser screenshot shows one matching title. One reviewer checked draft exclusion. The second reviewer could not run. The empty-result interaction has not been exercised.

    1. Compare the report with the checkpoint's promised outcome. Which required checks have evidence?
    2. Ask to operate the missing empty-result interaction. A screenshot of a match does not answer that question.
    3. Ask reviewers to challenge concrete aspects of the completed diff. One might trace behavior and integration; another might inspect ownership and missed failure cases.
    4. Require defects to be resolved or dismissed with evidence. Ask which checks were rerun after a repair.
    5. Make the human decision with the review limitation visible. Do not describe one review as two.

    For this exercise, assume you agreed to the full Helix-style checkpoint. The missing required review and interaction mean it is not ready under that agreement.

    What independent review contributes

    A reviewer can notice a mistaken assumption the implementer repeatedly accepted. Independence is stronger when the reviewer inspects the artifact and requirement before reading the implementer's defense. Agreement alone is weak if everyone only repeats the same summary. The reviewed object should be the actual diff and behavior evidence.

    What a screenshot can establish

    A screenshot can record a visible state, but may omit the action, timing, keyboard behavior, and persistence that led to it. Ask for a reproducible interaction or trace when those details matter. For search, distinguish a displayed result from proof that the entered query produced that result through the real request path.

    The local mindpattern-checkpoints skill describes an adaptation of this process. Your session permissions still govern commits, publishing, and production operations.     Lesson 12 · Lauren's replies · Coordinators and workers

    Give each agent a bounded responsibility

    Write a delegation brief with an outcome, ownership boundary, and proof.

    In the replies you supplied, Lauren explains that her Grok bot coordinates Cursor cloud agents, where much of her coding happens. Cloud-agent setup on the repository is a prerequisite for that arrangement. Our local agent tools are a different execution environment. Installing pstack does not establish the cloud connection.

    Split an example task

    1. Give a coordinator the reader outcome, constraints, and integration responsibility.
    2. Assign one worker the backend search change in its own writable checkout. Ask for the diff and executed evidence.
    3. Assign another worker an independent review of the feature map and browser contract. Keep that review read-only unless changes are explicitly assigned.
    4. Have the coordinator inspect the artifacts and test their integration. Individual worker success does not establish that the pieces work together.

    Write a delegation brief in your notebook. It should tell a worker what it owns, what it must leave alone, what input it can trust, and what evidence to return.

    Start with one verified workflow before multiplying workers. More agents can increase output while also increasing conflicts and review work. The benefit depends on how independently the tasks can run and how cheaply you can assess the result.

    What is a worktree?

    A Git worktree is another checkout of a repository with its own working files. Two workers can edit separate checkouts without typing over the same file. A cloud worker may instead have a separate machine. In both cases, shared services, ports, or databases can still conflict. Separate the state the workers mutate, then verify the combined result after integration.

    What a coordinator should return

    The coordinator should make the work understandable: the result, relevant tradeoffs, integrated evidence, unresolved issues, and the next decision. Forwarding several long worker transcripts makes you the integration layer. Ask for one account that cites the artifacts and explains any disagreement.

    When parallelism is a poor fit

    If task B cannot start until A defines a response contract, pretending they are independent often produces rework. Establish the shared contract first. Parallelize source investigation, separate experiments, or independent reviews where the inputs are stable. Keep tightly coupled edits with one owner unless there is a clear reason to split them.

    Each worker has a clear assignment and writable boundary. The coordinator owns the final integrated result.

    Common mistake. Spawning agents without defining who owns the shared files or who verifies their combined changes.

    Lesson 13 · Part 1 · Maintenance and useful memory

    Keep the verification loop accurate

    Turn one observed failure into a durable improvement to the checking process.

    A verification system can drift as the app changes. A route can move. A response field can change. A new entry point can bypass a rule that the existing scenario still checks correctly. Treat maintenance as checking the connection between instructions, tools, and current behavior.

    Audit one mapped feature

    1. Read the current feature entry and trace its entry points in source.
    2. Run the documented drive method against the intended instance.
    3. Compare the actual observations with the stated expectations.
    4. Classify a mismatch: outdated instructions, missing driver capability, or a product defect.
    5. Repair the responsible artifact within the authorized scope, then rerun the relevant proof.
    6. Preserve the evidence and record any remaining unsupported path.

    Practice with the draft-exclusion lab. Write the lesson you would encode after the first misleading green result. Prefer a concrete fixture and assertion over a generic instruction to be thorough.

    The installed maintenance skill can guide an audit. Its default editing scope is the verification skill's own directory. Our driver lives in verification/, outside that directory. A command repair therefore needs to be routed as an explicitly scoped code change rather than silently treated as a documentation edit.

    What should become memory?

    Keep information that changes the next decision or prevents repeated rediscovery. A sample draft with otherwise valid publication data can catch a filtering regression. A feature entry can explain a second user path that people repeatedly miss. A short handoff can record which branch and evidence belong to an unfinished task. A growing list of vague cautions is harder to apply.

    A maintenance schedule is an operating choice

    Lauren recommends frequent upkeep in Part 1. A useful cadence depends on how often the application changes and how the checks run. An available skill is not an active scheduled job. Before relying on automation, establish the environment, ownership, evidence location, and how failures reach an operator. This tutorial creates no schedule.

    Keep product repair and check repair distinct

    A maintenance audit can discover an application bug without being authorized to edit application code. Report the defect with a reproduction and route the fix to the normal implementation workflow. Respect the project's boundaries. Narrow tool permissions are useful only when the handoff for necessary work is clear.

    The audit produces either evidence of agreement or a specific mismatch with an owner and next check.

    Lesson 14 · Your practice · Bring the pieces together

    Lead one complete development cycle

    Export a brief and prompt sequence you can use to supervise a real, small task.

    Choose one behavior small enough to assess in a session. You can keep the remembered-title example or replace it with a real issue. If you choose a real issue, first establish whether it exists. The course's example is not evidence of a current defect.

    Assemble your next agent conversation

    1. Write the reader's action, expected outcome, constraints, and proof in your notebook.
    2. Ask for a restatement and investigation. Check whether the agent understood the problem and traced current behavior.
    3. Locate the verification skill, drive command, and feature entry. Identify missing proof before relying on the check.
    4. Where the design is uncertain, request a small number of runnable alternatives. Compare the same inputs and choose using the observed tradeoff.
    5. Ask architect to establish the code shape when the change needs that work. Then turn the selected design into verifiable checkpoints.
    6. Authorize the intended implementation scope in your own words. Let the agent handle routine details and require evidence for meaningful claims.
    7. Inspect the result, review findings, and proof limits. If a check misses a defect, improve the verification method as part of the repair.
    8. Update useful product knowledge and export your notebook for the next session.

    Use the prompt below as an opening, then adapt it. Do not paste every prompt from this course into one giant request. Move to the next phase when the previous phase has supplied the information you need.

    Assess your own progress

    Ask whether you can explain what the agent is trying to achieve, identify the evidence behind its claim, name what remains unverified, and give a useful correction.     Choose a smaller first real task
